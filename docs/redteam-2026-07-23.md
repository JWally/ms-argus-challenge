# Red-team report — ms-argus-challenge pairing captcha

**Date:** 2026-07-23
**Target:** `challenge-dev-jw.argus.pw` (embed at `www-dev-jw.argus.pw/captcha`), repo `ms-argus-challenge`
**Engagement:** authorized self-red-team of the post-refactor Challenge service. Read-only source review + black-box probing of the live `dev-jw` stack. No source or AWS state modified.
**Attacker goal modeled:** obtain a `paired` verdict / a merchant-trusted "pass" **without** a genuine two-device human presence.

---

## Bottom line

The refactor did **not** introduce a new protocol bypass. Every previously-closed defense from `ms-argus-pair` survived and is correctly re-implemented (see _Verified intact_). There is **no client-side path to forge a `paired` verdict token** — the HMAC anchor is sound.

At report time, the real exposure was unchanged from the old system: security
collapsed onto the **Argus fingerprint projection scores**, because the pairing
did not bind _the device that produced a scan_ to _the key that completed the
pairing_. The remediation branch now adds that binding by consuming the
verified cryptographic device id already present in the API projection. The
remaining findings are integration policy footguns and defense-in-depth
erosion.

Black-box confirmation on the live stack: sessions mint; `GET /info` does not leak participant tokens; a forged `desktop-attest` on a non-existent session returns `session_not_found`; the scoped-CPI format is enforced.

### Post-report remediation status

Work on `hardening/redteam-2026-07-23` addresses the locally actionable findings

### Delegated verification checklist — not run by the implementer

After deploying this branch to an isolated stack, the external verifier should:

1. Attempt to splice fresh clean Pair and SSO projection ids into attestations
   signed by unrelated throwaway keys. Pair must fail with a projection-device
   mismatch and SSO must fail with `sso_projection_device_unbound`. Then verify
   that current honest SDK scans still complete with both identities bound.
2. Capture the embed result message and confirm the merchant callback receives
   only `{sessionId, token}`. Patching the client-decrypted envelope must not
   create a browser-supplied verdict field, and `/api/verify` remains the final
   decision.
3. Rerun the worker-rewrite extraction harness in separate blob-substitution
   and same-origin response-rewrite modes. The CSP should block the former; the
   latter is expected to remain possible for a fully instrumented client and
   must still fail to forge a server verdict.
4. Rerun WebSocket origin/confusion cases with a disallowed handshake origin,
   a handshake/body mismatch, and a sealed connection envelope older than 300
   seconds.
5. Confirm a forced rate-limit-store failure returns
   `503 rate_limit_unavailable` without creating a session.
6. Rerun the normal Pair/Challenge success path so the security restrictions do
   not prevent an honest token from passing exact-CPI and exact-challenge
   `/api/verify`.

## Findings (ranked by real-world leverage toward the goal)

### 1. Projection provenance gap — the load-bearing weakness — **HIGH (by design)**

`argusSessionId` is taken from the request body (`packages/core/src/attestations/phone-attestation-request.ts:157`, `desktop-attestation.ts:79`) and the attestation is a **self-generated P-256 key with no root of trust** (`packages/adapters/src/crypto/attestation-verifier.ts` verifies the signature against the key _supplied in the same payload_). Nothing links the device that produced the fingerprint to the key/IP signing the attestation. Scoring judges the _fetched projection's_ IP/OS/browser (`packages/core/src/verdicts/projection-policy.ts`), never the requester's.

**Exploit:** harvest one clean phone scan + one clean desktop scan on devices/IPs you own → capture the two `argusSessionId`s. From a datacenter/automation box, script `start → desktop-attest → phone-attest` with throwaway keypairs, splicing in the two clean scan ids. For a default `integrity` CPI, `proofRequired` is false (`scoped-cpi.ts`), so no WebAuthn is needed → `verdict: paired`. One clean device pair mints unlimited verdicts for unlimited bot sessions.

**Bounds (not a fix):** the 180s freshness window and the single-use argus ledger force a _fresh_ scan pair per pairing, so throughput is gated by how fast clean scans can be produced on the farm.

**This is inherited, not new** — it is the "detector quality is the only universal lock" conclusion already in the prior attack log.

**Post-report mitigation:** the current API projection already exposes
`identification.crypto_device_id` as the first 10 hex characters of SHA-256
over the verified SPKI-base64 public-key string, plus `crypto_verified`.
Challenge now derives the same id from every Pair and SSO attestation public
key, requires verified identity, and fails the leg on a mismatch. This closes
the direct scan-splicing path without accepting a client-declared binding. It
is a practical mitigation rather than a full-strength cryptographic identity:
the merchant projection deliberately truncates the digest to 40 bits. A future
API contract should expose a longer server-verified binding identifier before
this is treated as a durable authentication primitive.

### 2. Unauthenticated `verdict` handed to the merchant — **HIGH if misintegrated**

`apps/web/src/features/embed/use-embed-session.ts:117-127` opens the verdict **client-side** from the AES envelope and posts `{verdict:'paired', token}` to the merchant. The `token` can be `null` — the verdict-token fetch error is swallowed in `desktop-flow.ts`. The loader then hands the whole `CaptchaResult` (`packages/contracts/src/browser/captcha-message.ts:1-6`) to the merchant callback.

```js
// use-embed-session.ts:117
const verdict = await session.result; // decided by CLIENT-decrypted envelope
const token = await session.verdictToken(); // server HMAC — may be null on error
postToHost(config.hostOrigin, { event: 'result', verdict: verdict.verdict, reason, token });
```

**Exploit:** a bot patches the embed JS so `verdict.verdict === 'paired'` (or forges the envelope with the shared reveal key, Finding 8). Any merchant integration that branches on `result.verdict === 'paired'` — instead of POSTing `result.token` to `/api/verify` and checking `passed` — is bypassed. A null token makes the failure silent.

**Fix:** stop emitting a decisive client verdict; deliver only the server token and require verification. See _Proposed fix #2_.

### 3. Client-chosen assurance scope — **MED**

The `.fastpass`/`.stepup`/`.forceauth` scope is parsed from the **client-supplied cpi suffix** at `/start` (`packages/core/src/assurance/scoped-cpi.ts:11`). A caller drops the suffix to select base `integrity` → `proofRequired:false`, downgrading step-up / fresh-proof requirements. The server binds cpi into the verdict claim (`verdict-token.ts:79` → `cpi_mismatch`), so this is safe **only if** the merchant verifies against the exact scoped cpi it intended.

**Fix:** treat scope as merchant policy, not caller input — enforce a per-cpi minimum scope server-side, and document that merchants must compare the returned `cpi`/scope to what they required. See _Proposed fix #3_.

---

### 4. Host-preflight is client-elective — **MED**

The only check that binds the flow to the real merchant origin/page is gated solely by the request body and required by **no** verdict rule.

```ts
// start-session.ts:92
const hostPreflightRequired = body.hostPreflightRequired === true;
// desktop-attestation.ts:36
if (!session.hostPreflightRequired) return { ok: true }; // whole binding skipped
```

`grep` confirms nothing else sets it and no verdict rule references the host binding. An attacker simply omits `hostPreflightRequired`. When present, the binding is solid (origin/cpi/challengeId/nonce/scanSessionId all enforced in `host-preflight.ts`).

**Fix:** drive it from cpi scope / a server default, not the request body. See _Proposed fix #4_.

---

### 5. Worker integrity is self-attested; QR pair-token extraction still open — **MED**

The QR worker hashes _itself_ (`apps/web/src/features/qr/qr-worker.ts` `selfHash` → `fetch(scope.location.href)`), and the server only confirms the reported hash matches the file served at the reported URL (`packages/adapters/src/http/worker-integrity.ts:43-52`). A page-realm attacker proxies `globalThis.Worker`, runs a rewritten worker that mints its own ECDH key to decrypt the sealed QR bundle, and reports the **honest** URL/hash — integrity "passes." There is still **no `worker-src` CSP** on the embed origin (`infrastructure/lib/site.ts:50-52` sets only HSTS/nosniff/referrer).

Your prior PoC `captcha-worker-rewrite-token-extract.mjs` still works. It yields the short-lived pair bundle (enables relay/co-attestation), not a direct forged verdict. The prior recommendation (strict `worker-src 'self'`) was never implemented.

Post-report compatibility finding: a strict same-origin-only policy also blocks
the signed Web Integrity runtime, which deliberately executes its fetched and
verified worker bytes through a blob URL to preserve the page origin and cookie
scope. Challenge therefore uses `worker-src 'self' blob:`. This retains a useful
deny-by-default boundary for data and cross-origin workers, but finding #5
remains only partially mitigated until Web Integrity has a non-blob worker
delivery design.

---

### 6. WebSocket origin gate checks a client-supplied body field — **MED (defense-in-depth only)**

`packages/core/src/relay/websocket-router.ts:89` validates `body.origin` (a self-declared JSON field), not the handshake header, and `$connect` returns `ok()` with no authorizer. The real access gate is the HMAC bootstrap token, so this is erosion, not a bypass. Related: the relay enforces **nothing about device distinctness** — it is a `(session, role)` router, and `/start` returns both role tokens to one caller. Fine today (distinctness lives in the HTTP attestation path); **never move device-binding onto the relay.**

### 7. Dev config posture — **operational (verify prod differs)**

The live `dev-jw` stack ships:

```
# infrastructure/lib/runtime-resources.ts:136-137
REQUIRE_PROOF_OF_LIFE: 'false'
ALLOW_TEST_AUTHENTICATORS: 'true'
```

inherited from `ms-argus-pair-dev-jw` (`.env.example` → `CHALLENGE_CONFIG_SOURCE_STACK`). So proof-of-life is off for default scopes and the blocklisted virtual authenticator is accepted. **Confirm prod flips both.** Note the WebAuthn `none`/single-AAGUID blocklist (`packages/core/src/proofs/virtual-authenticator.ts`) is bypassable by any software authenticator regardless — an accepted tradeoff (rejecting `none` breaks real iOS Touch/Face ID). Treat WebAuthn as interactivity proof, not an anchor.

### Low / informational

- **8. Sealed verdict envelope has no authenticity.** The AES-256-GCM reveal key is a per-session _symmetric_ key handed to both clients (`websocket-router.ts:163-173`); with key + `sessionId` a client can `sealFixedVerdictEnvelope(...'paired'...)` (`packages/contracts/src/verdicts/fixed-envelope.ts`). Confidentiality-in-transit only — the enabler for Finding 2. Contained today because nothing server/merchant-side re-ingests the envelope as authority.
- **9. SSO return code not consumed on proof-of-life failure** (`packages/core/src/sso/validation.ts:196`): the code isn't burned when `verifyProof` fails, so proof submission is retryable within the 90s window. Bounded; needs a fresh valid attestation each call.
- **10. Non-constant-time return-code hash compare** (`sso/validation.ts:72` uses `!==` vs `timingSafeEqual` elsewhere). Harmless — the value is a SHA-256 digest also bound into the signed attestation.
- **11. Rate limiter fails open** on limiter error (`start-session.ts:66`) — aids scan-farming for Finding 1, not a bypass alone.
- **12. Datacenter asymmetry:** `projection-policy.ts` fails a phone-side datacenter scan but not a desktop-side one (desktop blocked only on proxy + score). Confirm intentional.
- **13. WS envelope TTL (1h) far exceeds token TTL (300s)** (`websocket-router.ts:57`). Bearer routing-capability lives longer than needed; no cross-session reach. Tighten to the bootstrap TTL.

## Verified intact (the refactor preserved these correctly)

- **Verdict token unforgeable:** HMAC-SHA256, `timingSafeEqual`, server-only Secrets Manager key, exp/iat + cpi/challengeId context binding (`packages/core/src/tokens/verdict-token.ts`, `verdicts/verify-verdict.ts`).
- **argusSessionId single-use ledger:** atomic `attribute_not_exists(PK)` conditional write, and **both** legs claim (`dynamo-attestation-repository.ts:39`, `pair-runtime.ts:142`).
- **Atomic commits:** desktop (`attribute_exists(PK) AND attribute_not_exists(desktopAttestation)`) and phone (`attribute_not_exists(phoneAttestation)`) — no double-attest, no double-verdict, no verdict-forcing race. Phone must present a server-sealed desktop envelope; desktop cannot be skipped.
- **`same_device_both_sides` keyId check** (`phone-attestation-request.ts:168`), **projection fail-closed** (`projection_lookup_failed`), **freshness ±180s**.
- **SSO token machinery solid:** attestation re-verified at every leg (role/session/nonce/returnCode/cpi bound); approval tokens 256-bit, SHA-256 at rest, single-delivery, `timingSafeEqual`, single-use atomic. No forgery/replay/cross-session/cross-cpi/origin confusion found.
- **Client transport:** `parseCaptchaMessage` enforces both `origin` **and** `source` (cross-window / sibling-iframe forgery closed); no QR/frame-bundle downgrade (strict magic/version/length + trailing-byte rejection; GCM-authenticated ECDH seal); loader SRI matches the shipped bundle.
- **WS:** no cross-session leakage, no token forgery, sealed-envelope sender binding (`sender.connectionId === live socket`), HKDF key domain separation.

## Original proposed fixes

> These were drafted during the read-only engagement. The remediation table

### Proposed fix #2 — never hand the merchant a client-decided verdict

The merchant must trust only the server HMAC token. Deliver the token (and a neutral completion signal), not a decisive `verdict`. This is a **contract change** affecting merchant integrations — coordinate the rollout.

```diff
# apps/web/src/features/embed/use-embed-session.ts
     const verdict = await session.result;
     if (isCancelled()) return;
     const token = await session.verdictToken();
     update((current) => ({ ...current, completion: verdict.verdict }));
     postToHost(config.hostOrigin, {
       event: 'result',
       sessionId: session.sessionId,
-      verdict: verdict.verdict,
-      reason: verdict.reason,
-      token,
+      // No client-decided verdict crosses the trust boundary. The merchant
+      // MUST POST `token` to /api/verify and branch on `passed`.
+      token,
     });
```

```diff
# packages/contracts/src/browser/captcha-message.ts
 export interface CaptchaResult {
   sessionId: string;
-  verdict: string;
-  reason: string | null;
   token: string | null;
 }
@@ parseResult()
-  if (typeof payload.verdict !== 'string' || payload.verdict.length === 0) return null;
-  if (!isOptionalString(payload.reason) || !isOptionalString(payload.token)) return null;
+  if (!isOptionalString(payload.token)) return null;
   return {
     sessionId: payload.sessionId,
-    verdict: payload.verdict,
-    reason: payload.reason ?? null,
     token: payload.token ?? null,
   };
```

The local `completion` view-state (for the embed's own UI) can keep using `verdict.verdict`; it just must not be posted to the host.

**Interim stopgap** (if the full contract change can't ship immediately): never let a `paired` verdict cross the boundary without a token —

```diff
# apps/web/src/features/embed/use-embed-session.ts
     const token = await session.verdictToken();
+    // A paired result is only reportable if the server actually issued a token.
+    const reportedVerdict = token ? verdict.verdict : 'failed';
     postToHost(config.hostOrigin, {
       event: 'result',
       sessionId: session.sessionId,
-      verdict: verdict.verdict,
+      verdict: reportedVerdict,
       reason: verdict.reason,
       token,
     });
```

This does not remove the footgun (a merchant trusting `verdict` is still wrong), but it closes the null-token silent-pass path. Prefer the full change.

### Proposed fix #3 — bind assurance scope to merchant policy, not caller input

Server-side, enforce a per-cpi _minimum_ scope so a client cannot downgrade below what the merchant registered. Requires a policy source keyed by cpi (a config map or a projection field):

```ts
// sketch — packages/core/src/assurance/scoped-cpi.ts consumer at session start
const requested = parseScopedCpi(body.cpi);
const floor = await dependencies.merchantScopePolicy.minimumScope(requested?.cpi); // 'integrity' | 'stepup' | ...
if (requested && scopeRank(requested.scope) < scopeRank(floor)) {
  return { response: { status: 400, body: { error: 'scope_below_merchant_minimum' } } };
}
```

Until that policy source exists, this is **integration guidance**: the relying merchant must compare the `cpi` (including suffix) returned by `/api/verify` against the scope it required, and reject a downgrade. Document this prominently in the merchant integration guide.

### Proposed fix #4 — make host-preflight policy-driven, not attacker-toggled

Add a default (env-driven and/or per-scope) so the merchant page-origin binding can't simply be omitted:

```diff
# apps/api/src/runtime-config.ts  (RuntimeConfig + readRuntimeConfig)
+  hostPreflightRequiredByDefault: boolean;
@@ readRuntimeConfig()
+    hostPreflightRequiredByDefault: environment.REQUIRE_HOST_PREFLIGHT === 'true',
```

```diff
# packages/core/src/sessions/start-session.ts  (thread the default into validateStart)
-  const hostPreflightRequired = body.hostPreflightRequired === true;
+  const hostPreflightRequired =
+    body.hostPreflightRequired === true ||
+    dependencies.hostPreflightRequiredByDefault ||
+    scopedCpi?.proofRequired === true; // stepup/forceauth always bind the host page
```

Because host-preflight requires a valid `hostOrigin` + sealed host evidence, turning this on is a **behavior change for merchants** — stage it per-scope first (`stepup`/`forceauth`), then consider a global default once integrations send host evidence.
